# Project constitution

Rules and conventions every dev-pipeline persona follows in this project. Edit freely; the pipeline reads this file on every run.

## Specs location
Specs live in `specs/`: one folder per feature (`specs/<spec-id>/requirements.md` and `design.md`), plus `specs/_system/overview.md`.

## Commands
CI is `.github/workflows/ci.yml` (OPS-1): it runs the gate on `ubuntu-latest` and `windows-latest` on every push and pull request, and when `.github/workflows/release.yml` (OPS-2) calls it. Every other command below comes from the docs.

Toolchain: Rust `1.92.0` with rustfmt and clippy (`rust-toolchain.toml:2-3`), edition 2024 (`Cargo.toml:4`). CI installs the toolchain from `rust-toolchain.toml` (`rustup toolchain install` with no arguments) and names no version itself, so that file is the only place to change it.

**Path gotcha:** CLI paths are relative to the current directory. The defaults are `site/`, `meta/templates/`, `meta/assets/`, `dist/` and `mango.json`. None of these exist at the repo root; the sample site is under `example/` (`CLAUDE.md:45`).

## Conventions
- **Errors:** return `MangoError` via `?`. Where a category exists, add a variant to `src/error.rs` instead of using ad-hoc strings (`CLAUDE.md:66`). Seen in `src/config.rs` and `src/content/loader.rs`.
- **Path-specific I/O errors:** go through `MangoError::io_at(path, e)` (`CLAUDE.md:66`). Seen in `src/cli.rs`, `src/build/generate/assets.rs` and `src/build/output.rs`.
- **CLI:** clap derive style (`CLAUDE.md:67`). Seen in `src/cli.rs:20-84`.
- **Unit tests:** go in `#[cfg(test)] mod tests` next to the code. Filesystem fixtures are created per test under `target/unit-fixtures/<module>/...` (`CLAUDE.md:68`). Seen in `src/config.rs`, `src/content/loader.rs` and `src/build/output.rs`.
- **E2E tests:** live in `tests/build.rs` and run the compiled binary. They build either the fixture (once, via `fixture_dist()` into `target/integration-dist`) or per-test temp sites under `CARGO_TARGET_TMPDIR`. They check exit status, stderr and output files, and reuse the existing helpers (`run_mango`, `temp_dir`, `build_temp_site`, `build_with`, `snapshot`, `assert_success`, `assert_failure`, `assert_previous_output_intact`, `built_site_with_private_templates`) (`CLAUDE.md:68`; `tests/build.rs`).
- **Fixtures:** `example/site`, `example/meta` and `example/mango.json` are committed and cover every success-path feature. `build_generates_site_from_fixture` checks the exact output manifest, and the `fixture_*` tests check the rest. Error-case files never go in the fixture; they are built in test code. `example/dist` is generated and gitignored (`CLAUDE.md:69`, `.gitignore:2`).
- **Build pipeline order:** load, plan assets, build one list of outputs (pages, sections, home, tags, feed, sitemap, then asset copies), check collisions over that list, render everything in memory, run the safety check, and only then clean and write. A new kind of output is a new `OutputKind` variant, so it goes through `output::check_collisions` and is rendered before anything is cleaned (`CLAUDE.md:49-51`; `plan` and `commit` in `src/build/pipeline.rs`).
- **Strict inputs:** dates, tags, file names and `base_url` are validated strictly. Bad values fail the build with an error naming the file and the value. Drafts are validated too (`CLAUDE.md:7-11, 29`).
- **Feed and sitemap** are generated in Rust, not Tera. XML escaping goes through `build/generate/xml.rs` (`CLAUDE.md:13`, `CLAUDE.md:62`).
- **Acceptance-criteria IDs:** tests are tagged with `// AC-<...>` comments that point to acceptance criteria; they appear in 18 files. **Decided by the maintainer (2026-09-17, SPEC-1): new criteria are spec-scoped, `AC-<spec-id>.<n>`.** `<spec-id>` is the spec's kebab-case id, so `// AC-arch-1.3` resolves to `AC-arch-1.3` in `specs/arch-1/requirements.md` with no lookup table. Two specs cannot collide, and the numbering needs no central register that goes stale — which is what replaced the previous proposal that new specs start at group `AC-10`. That proposal was withdrawn because it was already false: groups `AC-1` through `AC-12` are all in use today, one more is consumed by every spec-driven run, and any number written here is wrong again after the next one.
- **Legacy numeric IDs.** The 181 existing `AC-<group>.<n>` tags stay for now, and do not resolve: groups `AC-1` to `AC-9` were each defined four times over by four separate `tasks.md`-driven batches, only 56 of the 181 tags carry a `(batch N)` qualifier, and every definition lives in the gitignored `.dev-pipeline/runs/**`. Their definitions are now published in [`specs/_system/legacy-criteria/`](_system/legacy-criteria/README.md) (SPEC-2): 201 criteria across 48 requirements, verbatim, with the test that verified each one. A numeric tag is therefore resolvable but not self-identifying — look it up by the **test's name**, which is unique, not by the number. Rewriting the tags themselves into spec-scoped form is [SPEC-3](_system/backlog.md#spec-3), scheduled after ARCH-1 because that item moves and deletes many tag sites. A tag on a **withdrawn** criterion is removed rather than reassigned (precedent: `publish_is_not_a_command`, FEAT-2).
- **Git workflow.** **Decided by the maintainer (2026-09-16):** work happens on a feature branch and lands on the integration branch by **squash merge**, one commit per backlog item or feature. Since 2026-09-24 it lands through a **GitHub pull request** (GitHub flow; see **Landing** below): the maintainer squash-merges it on GitHub. The squashed commit's subject names the backlog item ID where there is one, e.g. `… (RISK-2)`, so `git log --grep` resolves an item to the change that closed it. Because squashing discards the branch's intermediate commits, write the squashed message to stand on its own: what changed and why, not "address review". Squashing also rewrites hashes, which is why the backlog records item IDs rather than commit hashes (`specs/_system/backlog.md:3`). Delete the branch once it has landed. **Branch before the work starts, not after** (2026-09-17): a dev-pipeline run creates its branch at step 3.4 before any persona runs and commits a checkpoint after each stage that changes files, so a run's output is never left uncommitted on the integration branch and a bad stage can be reset to the previous checkpoint rather than to the run's start. Only the orchestrator touches git, and only additively — branch, checkpoint and, when the maintainer says **“land it”**, push that branch and open its pull request; personas may read git but never change it (`.claude/commands/run-workflow.md`, step 0). Backlog items are no longer marked `in progress` before a run: the branch is that signal, and the item goes `open` → `done` in the squash commit, which is the merged pull request.

  **Integration branch (2026-09-17).** The branch work lands on. Resolve it, in order: (1) `git symbolic-ref --short refs/remotes/origin/HEAD` with the `origin/` prefix stripped — authoritative once a remote exists, so adding one whose default is `main` needs no change here; (2) otherwise whichever of `main` or `master` exists as a local branch; (3) if both exist, or neither does, **stop and ask** — never guess, because the wrong choice means branching from or merging into the wrong history. Today it resolves to `master` through rule (1), `origin/HEAD`. A run records it as `integration_branch` in `state.json` at the start-state gate, so the gate, the final report and any resume all use one value. Everything below says “the integration branch” and means the resolved value, not a literal.

  **Branch naming (2026-09-17).** Two namespaces on one axis — who did the work — both ending in `<id>-<short-desc>`: the backlog item ID lowercased, then two to four kebab-case words describing the change, not the prompt that requested it. The `<id>-` segment is dropped when there is no backlog item.
  - `agents/claude/<id>-<short-desc>` — work done by an agent, whether through a dev-pipeline run (`run-workflow.md` step 3.4) or directly in a session.
  - `users/patrick/<id>-<short-desc>` — work done by hand.

  Both `<name>` segments are literals fixed here, not derived from `git config user.name` or from the model in use, so they cannot drift when a remote introduces different account handles. Before creating a branch, check for an existing `*/<id>-*` and ask rather than opening a second branch for the same item: the per-actor namespaces mean two people working one item no longer collide by name, and this check is what replaces that signal. Delete the branch once it has landed. The checkpoint commit subject keeps its `pipeline(<run_id>)` prefix: that names the machinery that produced the commit, a different axis from who did the work, and the squash discards it regardless.

  **Starting a run (2026-09-17).** A run starts from the integration branch with a clean tree, or it does not start. The integration branch must also be up to date with `origin`: after `git fetch`, a local branch behind `origin/<int>` stops the run with an offer to `git pull --ff-only`, since branching from a stale tip builds on history that has already moved. On any other branch — hand-done work under `users/…`, or an `agents/claude/…` branch from an earlier item that never landed — the orchestrator stops **before creating anything**, so a refused run leaves no `.dev-pipeline/runs/` folder behind, and asks the maintainer to finish and land that work first. Starting from the integration branch anyway, or deliberately stacking on the current branch, are both available but must be chosen explicitly; a deliberate stack is recorded as `branch_point_override` and its squash consequence is repeated in the run's final report. A dirty tree always stops: checkpointing needs a clean tree, and the pre-branch escape hatch that let a run proceed with no branch and no checkpoints is withdrawn.

  **Reading a branch's change.** Diff against the branch point (`git diff <branch_point>..HEAD`) plus anything still uncommitted. A bare `git diff` is empty once a run has checkpointed, which reads as “no change” and is wrong. The orchestrator passes `branch`, `branch_point` and `checkpoints` to every persona so neither the Tester nor the Reviewer has to re-derive them, and both record a `commit:` in their artifact frontmatter — the Tester so the maintainer can tell whether the squashed tree is still the one that was verified, the Reviewer so its next attempt can diff from where it last looked rather than guessing at a checkpoint.

  **Remote (decided 2026-09-17, revised 2026-09-25).** The remote is `https://github.com/pblanc5/mango`, default branch `master`. The repository was private when the remote was added and is now **public** (noted by the maintainer on 2026-09-25), so everything that lands (code, specs, docs, the changelog, pull request descriptions) is publicly readable. The maintainer added the remote by hand on 2026-09-24; OPS-1 did not add it, it only added CI. The repository allows **squash merges only**, uses the pull request's title as the squash commit's subject and its body as the message, and deletes a branch when its pull request merges; so every merge, even one made in the web UI, is one commit per item. A pipeline run's own verification remains the Tester's local gate; CI is the check on the pull request.
  - The orchestrator pushes only an `agents/claude/…` branch it created, and only after the maintainer says “land it”. It never pushes the integration branch, never force-pushes, and never pushes on its own initiative.
  - The orchestrator may open a pull request (`gh pr create`), update the title or body of one it opened (`gh pr edit`), and read its state (`gh pr view`, `gh pr checks`). Reviewing, approving, merging and closing are the maintainer's: it never runs `gh pr merge`, `gh pr review`, `gh pr close` or any other `gh` write.
  - The Reviewer's verdict stays an artifact in `.dev-pipeline/`. Approving a pull request is a human act; the pipeline review is a pre-flight check, not a substitute for it.
  - No persona uses `gh` or any other network write.

  **Landing (2026-09-24).** GitHub flow, one pull request per item, replacing the local squash merge.
  1. The maintainer says **“land it”**. The orchestrator pushes the branch (`git push -u origin <branch>`) and opens a pull request against the integration branch with `gh pr create`. The **title** is the squash commit's subject, with the backlog item ID where there is one (`… (OPS-1)`). The **body** is the squash commit's message, so it must stand on its own as described under **Git workflow**, and it ends with the commit's `Co-Authored-By` trailer.
  2. The orchestrator reports the pull request's URL and waits for CI (`gh pr checks --watch`). A red check is reported with its failing test and cause. A fix goes on the same branch, as a new commit that is pushed, and only when the maintainer asks for it; the pull request's body is updated if the fix changes what the squash commit should say.
  3. The maintainer reviews the pull request on GitHub and merges or closes it.
  4. When the maintainer says it is merged, the orchestrator confirms it (`gh pr view <n>`), checks out the integration branch, `git pull --ff-only`, deletes the local branch and runs `git fetch --prune`, so the next branch starts from the merged tip.

  CI's `pull_request` run tests the merge of the branch into the current integration branch, so it re-checks the gate when the integration branch has moved since the branch point. The Tester records the commit it tested, so the maintainer can tell whether the pull request's head is still the tree the pipeline verified.

  **Releasing (2026-09-25, OPS-2).** A release is a GitHub Release with a `vX.Y.Z` tag on a commit on the integration branch, with prebuilt binaries attached. mango is not published to crates.io.
  - **Versions** follow [Semantic Versioning](https://semver.org), applied to what a site author relies on: CLI commands, flags and exit codes, content and frontmatter rules, `mango.json`, template names and contexts, and output URLs. The library is an internal seam and carries no version promise. Before 1.0, a breaking change bumps the minor version and anything else the patch version.
  - **`CHANGELOG.md`** follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every pull request that changes something a site author sees adds a line under `## [Unreleased]`, in the group that fits (Added, Changed, Deprecated, Removed, Fixed, Security), written for site authors. Internal changes (refactors, tests, CI, specs) get no entry.
  - **Targets:** `x86_64-unknown-linux-musl` (statically linked) as a `.tar.gz` and `x86_64-pc-windows-msvc` as a `.zip`, the two platforms CI tests. Each archive, `mango-vX.Y.Z-<target>`, holds the binary, `README.md`, `LICENSE` and `CHANGELOG.md`; a `SHA256SUMS` file covers both.

  Cutting a release:
  1. **Release pull request.** On `agents/claude/release-X-Y-Z` (or `users/patrick/release-X-Y-Z`), titled `Release vX.Y.Z`, it bumps `version` in `Cargo.toml` and `Cargo.lock`, renames `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD` with a new empty `## [Unreleased]` above it, and updates the link references at the bottom (`[Unreleased]` compares `vX.Y.Z...HEAD`; `[X.Y.Z]` compares the previous tag, or points at the release for the first one). Nothing else changes. It lands through **Landing** like any other pull request.
  2. **Release workflow.** After it merges, the maintainer runs **Release** (`.github/workflows/release.yml`) from the Actions tab on the integration branch. It refuses any other branch, reads the version from `Cargo.toml`, refuses a tag that already exists, takes the notes from that version's `CHANGELOG.md` section (refusing a missing or empty one), runs the CI gate, builds each target with `--release --locked`, checks that the binary reports that version, packages the archives, and refuses a release that already exists, drafts included. It then creates a **draft** Release on the commit it ran on, with the notes and the archives attached.
  3. **Publish.** The maintainer reviews the draft and publishes it; GitHub creates the tag then. Until that point nothing is public and no tag exists, so a bad draft is deleted and the workflow run again.

  An agent may prepare the release pull request and draft its changelog section. Running the Release workflow, creating or deleting tags, and publishing or editing Releases are the maintainer's: an agent never runs `gh workflow run`, `gh release`, `git tag` or `git push --tags`.
- **Designs and design amendments (OPS-3, 2026-09-25).** Two rules for spec-driven runs, from what went wrong in RISK-4:
  - **Evidence for external behavior.** The Architect backs every claim about how a dependency, the standard library, the compiler or the OS behaves with evidence: a source line in the locked version, fetched documentation, or an existing test. A claim it can't verify is listed under **Unverified assumptions** in the design's Risks, and the first safety-net task is a test that proves it. RISK-4's design v1 made two unverified claims about serde that were false; under this rule they would have failed at the first task.
  - **Design-only findings go back to the design stage.** When the code is right and the published design is wrong, the Developer departs from the design inside its listed Files, records it under Deviations as **design amendment needed** with the evidence, and never edits the design itself. The Reviewer, once every remaining finding is in the design, requests changes with `route: design`, and the orchestrator sends the run to the design stage (`on_design_changes` in `spec-feature.yaml`, at most twice). The amended design stops for the maintainer's approval like any design, then develop, test and review run again. `scope_change` stays reserved for wrong requirements. Before this, the same situation forced a `scope_change` stop and a manual `--resume --from design`.
- **Module layout:** folder modules use `mod.rs` (`src/build/mod.rs`, `src/content/mod.rs`, `src/render/mod.rs`, `src/build/generate/mod.rs`, `src/build/index/mod.rs`).
- **Template names** (`page.html`, `section.html`, `home.html`, `tags.html`, `tag.html`) are hardcoded in `src/render/template.rs` (`CLAUDE.md:61`).

## Non-negotiables
From the documented "Definition of done" (`CLAUDE.md:71-82`) and the maintainer's decisions in this run:
- **The gate passes** (`cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`), with no new warnings and no `#[allow]` added to hide one (source: `CLAUDE.md:75`).
- **No dead code, and no `#[allow(dead_code)]`.** Unused code is removed, not kept "for later" or silenced. There are no exceptions (source: maintainer decision, run `20260914-223413-bootstrap-specs-for-this-project`). The unused `ServerOpts` (`run`'s `--address`/`--port`) was removed after this run; `run` takes no options until it is implemented (`run_command_takes_no_options`).
- **Every behavior change or bug fix has a test that fails without it.** Anything visible from the CLI also gets an E2E test in `tests/build.rs` (source: `CLAUDE.md:76`).
- **A new success-path feature adds fixture content** and updates the `build_generates_site_from_fixture` manifest plus a `fixture_*` test. Error cases use temp-site E2E tests, never fixture files (source: `CLAUDE.md:77`).
- **Bad input fails before the output folder is cleaned,** proven with a `snapshot` test. The error is a `MangoError` on stderr with exit status 1, naming the file or path and the bad value (source: `CLAUDE.md:78`).
- **Output is deterministic, and a test enforces it.** Two builds of the same input must be byte-identical (sorted listings, no timestamps) (source: `CLAUDE.md:79`). The maintainer decided in this run that an automated test must check this: `fixture_build_is_deterministic` in `tests/build.rs` builds the fixture twice and compares every file.
- **Links and XML stay valid:** every internal link in the fixture output resolves (`fixture_internal_links_resolve`), and generated XML is escaped (source: `CLAUDE.md:79`).
- **No new dependencies without the maintainer's explicit approval.** Removing one is fine (source: `CLAUDE.md:80`). `tide` has been dropped (commit `dc66348`, not in `Cargo.toml`). Any remaining reference to it is stale and gets removed, not followed (source: maintainer decision, this run).
- **Docs change with the code:** `README.md` and an `Unreleased` line in `CHANGELOG.md` for anything a site author sees (see **Releasing**), `CLAUDE.md` for architecture, pipeline order and conventions (source: `CLAUDE.md:81`).
- **No TODO stubs, commented-out code, or `unwrap`/`expect` in production code.** Known limitations are listed in `README.md` (source: `CLAUDE.md:82`).
- **`ensure_safe_to_clean` must keep refusing** to clean the cwd, its parents, or a folder that is or contains the site, templates, assets or config (source: `CLAUDE.md:51`, `README.md:99`).
- **HTML output stays root-relative.** `base_url` is used only by the feed and sitemap (source: `CLAUDE.md:7`).

## When to use /spec-feature
**Confirmed by the maintainer (2026-09-17, SPEC-1).**
- **Use `/spec-feature` for:**
  - public or interface changes: CLI subcommands or flags, config fields in `mango.json`, template names or template context fields
  - data or format changes: frontmatter rules, slug/URL/output path rules, feed or sitemap format
  - behavior site authors rely on: validation strictness, collision rules, clean safety, ordering of listings
  - changes across multiple components, e.g. a new output type touching `content/`, `render/`, `build/` and `cli.rs`
  - anything that needs a new dependency
- **Use `/ship-feature` for:**
  - small local changes and bug fixes inside one module
  - internal refactors covered by existing tests, including dead-code removal that doesn't change the CLI surface
  - test-only changes, such as adding the determinism test
  - docs-only changes (`README.md`, `CLAUDE.md`)
  - **removing an unimplemented surface.** A CLI subcommand or flag that only ever returned an error has no behavior to specify, so taking it out is not an interface change in the sense above. Dropping `publish` (FEAT-2) went this route deliberately; adding or changing a surface still needs `/spec-feature`.

## Related docs
- `CLAUDE.md`: architecture, pipeline order, template contexts, module map, conventions and the definition of done. This is the authoritative developer doc.
- `README.md`: the user guide (commands and flags, content rules, config, output URLs, templates, safe builds, known limitations).
- `example/mango.json`, `example/site/`, `example/meta/`: the fixture site that shows every success-path feature.
- `specs/_system/backlog.md`: tracked improvements (architecture review, risks, gaps) with IDs, priorities and suggested workflows. Update an item's status when work on it starts and when it lands.
- `LICENSE`: GPL-3.0-or-later.
- `.github/workflows/ci.yml`: CI, which runs the gate on Linux and Windows on every push and pull request.
- `.github/workflows/release.yml` and `CHANGELOG.md`: the release workflow and the user-facing changelog (see **Releasing**).
- `.claude/pipeline/workflows/*.yaml`, `.claude/commands/*.md`: dev-pipeline workflow definitions.

`tasks.md` (gitignored, local only) is not project policy, and the pipeline should not use it as a source of rules.
