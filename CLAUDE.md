# mango

A static site generator CLI written in Rust (edition 2024, toolchain pinned in `rust-toolchain.toml`). Licensed GPL-3.0-or-later (`LICENSE`). `README.md` is the user-facing guide; this file is for working on the code. Planned improvements and known gaps are tracked in `specs/_system/backlog.md`: check it before starting related work, and update an item's status when you pick it up or finish it.

Pipeline: load markdown files (`.md` / `.markdown`, any case) → parse frontmatter → load the site config → render markdown with pulldown-cmark → render through Tera templates → write `dist/<slug>/index.html` per page (plus a section index page for every folder level, the home page at `dist/index.html`, the tag index at `dist/tags/index.html` and one `dist/tags/<tag>/index.html` per tag) → write `dist/feed.xml` and `dist/sitemap.xml` (only when `base_url` is set) → copy assets into `dist/assets/`.

**Site config is JSON too** (`src/config.rs`, `SiteConfig`). `build --config <path>` (default `mango.json`, cwd-relative). The default file is optional (missing → defaults); an explicitly given `--config` that doesn't exist is an error naming the path. `#[serde(deny_unknown_fields)]`: malformed JSON, unknown fields (typos) or a bad `recent_count` fail with `MangoError::Config` naming the file. Fields, all optional: `title`, `author`, `description`, `base_url` (strings), `recent_count` (non-negative integer, default 10). `base_url`, when set, must start with `http://` or `https://` (case-sensitive prefix check; `""` and `example.com` are rejected) — otherwise `MangoError::Config`: `'<path>': invalid base_url '<value>': must start with http:// or https://`. Templates get `base_url` exactly as written; HTML output never uses it (generated HTML URLs stay root-relative). Only the feed and sitemap use it, via `config::base_url_root`, which trims trailing `/` so `https://example.com/` and `https://example.com` give identical links. The config file path is protected from cleaning (see below). See `example/mango.json`.

**File names are strict.** Every segment of a page's path relative to the site folder (folders and the file stem) may only contain ASCII letters, digits, `-`, `_` and `.` (`content::slug::Slug::from_content_path`, called last in `Page::new`), so URLs, the feed and the sitemap never need percent-encoding. Anything else (spaces, non-ASCII, `+`, an empty segment) is a `General` build error naming the file and `'<segment>'`: `<file>: invalid file name '<segment>': use only ASCII letters, digits, '-', '_' and '.'`, drafts included. A segment made only of dots (`...md` and `..md` both give `..`) can write outside its own folder or silently onto another output, so every dot-only segment is rejected (deliberately uniform), with its own message: `<file>: invalid file name '<segment>': a segment cannot consist only of dots`. A `Slug` only exists after that validation (or as a derivation of a valid one: `parent()`, `Tag::slug`, `Slug::home()`, `Slug::tag_index()`) and owns every slug rule: `url()`, `output_path(dist)`, `parent()`, `is_top_level()`, `segments()`. It orders byte-wise on the `/`-joined text (`a-c` before `a/b`) and serializes and displays as that text. On Unix a `\` in a file name becomes a `/` (RISK-6).

**Tags are strict, like dates.** Each tag must match `^[a-z0-9]+(-[a-z0-9]+)*$` (lowercase ASCII letters/digits, single hyphens between; checked by hand in `content::tag::Tag::parse`; `Tag::parse_list`, called from `Page::new`, parses and de-duplicates a page's tags). Anything else — `""`, `Rust`, `static site`, `c++`, leading/trailing/double hyphens, non-ASCII — is a `Frontmatter` build error naming the file and `'<tag>'`, drafts included. Duplicate tags are dropped, first occurrence keeps its place. The tag is its own slug (no slugify): tag pages are at `/tags/<tag>/` (`Tag::slug` / `Tag::url`), the tag index at `/tags/` (`Slug::tag_index`). The tag index is **always** generated (even with no tags), so `/tags/` is reserved: a `tags/` content folder (`section index 'tags'`) or a top-level `tags.md` (`page 'tags'`) collides with `tag index` and fails the build.

**Feed and sitemap** (`build/generate/{feed,sitemap,xml}.rs`) are generated in Rust, not Tera (fixed format; escaping of `& < > " '` via `xml::escape`), and only when `base_url` is set — otherwise neither file is written and the build still succeeds. No `lastBuildDate`/`now()`; output is deterministic.
- `feed.xml` (collision label `RSS feed`): RSS 2.0; channel `title`/`description` from config (empty when unset), `link` `<base>/`; one `<item>` per entry of `home::recent_pages` (the same list as `home.recent`, in order) with `title`, `link` (`<base><url>`), `<guid isPermaLink="true">` (same), `description` (frontmatter), `pubDate` (`Sat, 24 Jan 2026 00:00:00 +0000`).
- `sitemap.xml` (collision label `sitemap`): sitemaps.org 0.9 `<urlset>`; one `<url><loc>` per HTML output (home, pages, sections, tag index, tag pages — derived from the outputs' kinds, not the content; the feed, the sitemap and assets are skipped by kind), sorted by `loc` as plain strings; `<lastmod>YYYY-MM-DD</lastmod>` only for dated content pages (the date carried by `OutputKind::Page`).

**Template contexts** (Tera autoescape is on for `.html`, so print URLs with `| safe`):
- every template: `config` — always has all five keys; unset strings are JSON `null` (renders empty, falsy, and triggers `default(...)`; `""` would not).
- `page.html`: `page` — `title`, `author`, `description`, `date`, `tags` (list of `{ name, url }` objects, `url` = `/tags/<name>/`, frontmatter order after dedup), `url` (`/<slug>/`), `content`.
- `section.html`: `section` — `slug`, `url`, `pages` (direct child page summaries: `title`, `date`, `slug`, `url`), `subsections` (direct child sections: `slug`, `url`, sorted by slug).
- `home.html`: `home` — `recent` (up to `config.recent_count` dated pages site-wide, section ordering, undated dropped) and `sections` (top-level sections: `slug`, `url`, `page_count` = direct child pages).
- `tags.html`: `tags` — the list itself (not wrapped): `{ name, url, page_count }` sorted by name; empty when no page has tags.
- `tag.html`: `tag` — `name`, `url`, `pages` (page summaries with that tag, section ordering, undated included and last).
- Page summaries (`section.pages`, `home.recent`, `tag.pages`) have no `tags` key.
- `page.html`, `section.html`, `home.html`, `tags.html` and `tag.html` are all required (names hardcoded in `render/template.rs`); a missing one fails at render time, before cleaning (`tags.html` is needed by every build; `tag.html` by any build with at least one tag).

**Markdown extensions** enabled in `render/markdown.rs`: tables, footnotes, strikethrough, task lists, explicit heading attributes (`# Title {#my-id}`). No auto-generated heading IDs.

**Frontmatter is JSON, not YAML** — a `---`-delimited block containing a JSON object (see `example/site/blog/how-i-write.md`); a leading UTF-8 byte order mark is ignored. Line endings may be LF, CRLF or a mix: `str::lines` drops the `\r`, so the delimiters match and the JSON block is re-joined with `\n`, and the body is normalized to LF (its final newline dropped), so a CRLF content file and its LF twin build byte-identical output. The one exception is the "no frontmatter" early return, which hands the content back verbatim, CRLF included; it is unreachable from the CLI, since `loader::load` turns it into the missing-frontmatter error. Only content is normalized: templates are rendered and assets copied with whatever line endings they have. Pinned by the CRLF tests in `frontmatter.rs` and `tests/build.rs`; TEST-1 in `specs/_system/backlog.md` records what each of them can and cannot catch. Required fields: `title`, `author`, `description`, `draft`; optional: `date`, `tags` (see the tag rules above). `date` must be a strict `YYYY-MM-DD` string (parsed into `Option<chrono::NaiveDate>` by `page::parse_date`); a present but invalid or impossible date — including `""`, and on draft pages — is a build error naming the file and the value. Templates still see `page.date` / `section.pages[].date` as `"YYYY-MM-DD"`, or `""` when unset. A markdown file without frontmatter (`<file>: missing frontmatter: …`) or with malformed frontmatter, at any depth, is a build error naming the file. Pages with `"draft": true` are still parsed but excluded from output and section indexes (filtered in `loader::load`).

## Commands

```sh
cargo build
cargo test          # unit tests + tests/build.rs integration tests (fixture build + temp-site error cases)
cargo clippy --all-targets -- -D warnings
cargo fmt

# Run against the fixture site (paths are cwd-relative!):
cd example && cargo run -- build
# or from the repo root:
cargo run -- build --site example/site --templates example/meta/templates --assets example/meta/assets -o example/dist
```

**Path gotcha:** all CLI paths resolve relative to the current working directory, with defaults `site/`, `meta/templates/`, `meta/assets/`, `dist/`. The repo root has none of these — the sample site lives under `example/` (`example/site`, `example/meta`; generated `example/dist` is gitignored). **CI** (`.github/workflows/ci.yml`) runs the gate below on Linux and Windows on every push and pull request, with the toolchain from `rust-toolchain.toml`.

## CLI surface (`src/cli.rs`) and the plan/commit seam

- `build` — the only real subcommand. `cli.rs` only parses arguments and dispatches: it turns `BuildOpts` into a `mango::BuildOptions` and runs `commit(plan(&opts)?)`. The pipeline itself lives in `src/build/pipeline.rs` and is **two phases**. `plan(&BuildOptions) -> BuildPlan` does everything that can fail on bad input and writes nothing. Order: load pages → load config → load templates → resolve assets destination (an assets path with no final name, e.g. `.`/`..`, is an error) → plan assets (`assets::plan` lists every asset file; a missing assets folder fails here, as does a symlinked folder or an unresolvable symlink inside the assets folder) → build **one** `Vec<Output>` in a fixed order: pages, section indexes, home page, tag index, tag pages, then the generated `feed.xml` and `sitemap.xml` (in memory; the sitemap picks the HTML outputs out of that list by kind; both skipped without `base_url`), then the asset copies, last → collision check over that list, in that order → `output::render` turns the list into `RenderedOutput`s in memory: **every** page, section, home and tag template rendered to a string, generated text passed through, asset copies kept as copies. `commit(BuildPlan)` then does the rest, in order: safety check → empty the output folder → `output::write` in one pass over the list (every file is written, then every asset is copied, because assets come last). Nothing is deleted or written until loading, planning and rendering have succeeded, and that is now a property of the seam rather than of statement order: `commit` accepts only a `BuildPlan`, and only a successful `plan` produces one (`BuildPlan`'s fields are private and `plan` is its sole constructor). So a bad page, bad file name, bad tag, bad config (incl. `base_url`), missing templates or assets folder, an output conflict or a Tera render error leaves the previous output untouched (an I/O failure after the clean can still leave partial output). A plan is bound to the output folder it was planned against — `BuildPlan::output_dir()` names it and `commit` takes no destination — and `BuildPlan::outputs()` enumerates every file it would write (path relative to the output folder plus the exact bytes) and every asset copy, so a caller can inspect a build without committing it.
  - **Collisions:** two outputs mapping to the same file (e.g. top-level `posts.md` and the `posts/` section index — including an ancestor index: `a.md` next to `a/b/c.md`; `tags.md` / a `tags/` folder vs the tag index; `site/assets.md` vs an asset `index.html`) fail with `MangoError::General` naming the path and both labels (derived from each output's `OutputKind`: `page '<slug>'`, `section index '<slug>'`, `home page`, `tag index`, `tag page '<tag>'`, `RSS feed`, `sitemap`, `asset '<relative path>'`). So does a file-vs-folder conflict, where one output is a file at a path another output needs as a directory (`site/feed.xml.md` → `dist/feed.xml/index.html` vs `dist/feed.xml`; `site/assets/minimal/main.css.md` vs the asset `minimal/main.css`). `posts/index.md` → `posts/index/index.html` is not a collision.
  - **Cleaning:** the output folder's contents are removed (folder kept, symlinks removed not followed; a symlink `remove_file` can't delete falls back to `remove_dir`, for Windows directory links). `ensure_safe_to_clean` refuses an output path that is the cwd, a parent of the cwd, or equal to / a parent of the site, templates or assets folder or the config file (canonicalized comparison).
- `clean` — removes the dist dir; a missing dir is success. Same safety check, protecting the cwd, its parents, and the default `site`, `meta/templates`, `meta/assets` (not the config file; `clean` has no `--config`). It lives in `src/build/clean.rs` (`mango::clean`) together with `ensure_safe_to_clean` and `clean_contents`, not in `cli.rs`.
- `run` (dev server) — not implemented; takes no options, returns an error and exits 1. There is no `publish` subcommand: it was dropped rather than implemented (backlog FEAT-2), so `mango publish` is a clap “unrecognized subcommand” error, pinned by `publish_is_not_a_command`. Add `run`'s flags and a server dependency (with approval) when it is implemented, not before: unused code is removed, never kept behind `#[allow(dead_code)]`.

## Module map

- `src/lib.rs` — library root. Every module below it is **private**; the public surface is exactly seven re-exports: `plan`, `commit`, `clean`, `BuildOptions`, `BuildPlan`, `PlannedOutput`, `MangoError`. Keeping the modules private means a `pub` item nothing uses still trips the dead-code lint, so "no dead code" stays compiler-enforced everywhere but those seven names. The library is an **internal seam** for the binary and the in-process tests (and, later, the dev server): it may change freely, is not documented in `README.md`, and carries no semver promise.
- `src/main.rs` — binary entry; `mod cli;` plus `main()`, which calls `cli::run()`. On error prints to **stderr** and exits 1; exits 0 on success.
- `src/cli.rs` — **binary only** (declared by `main.rs`, not by `lib.rs`, so clap never enters the library). Holds the clap structs, flag defaults and help text, `BuildOpts::into_options()` and the dispatch of `build`/`clean`/`run` — no pipeline step, no safety check, no cleaning logic.
- `src/config.rs` — `SiteConfig`, `load(path, explicit)` (incl. `base_url` validation) and `base_url_root`.
- `src/error.rs` — `MangoError` (thiserror): `Io`, `IoPath { path, source }`, `Frontmatter`, `General`, `Config`, `Template`. Display includes the underlying cause (for `Template`, the full Tera `source()` chain). Use `MangoError::io_at(path, e)` for I/O failures on a specific file/dir.
- `src/content/` — `loader.rs` (recursive site traversal; `is_markdown`; propagates errors at every depth; drops drafts; classifies each entry with `fs::metadata` plus a non-following `is_symlink` check before descending, so a symlinked folder is a `General` error (`content folder '<rel>' is a symlink to a directory`) instead of being followed and re-walked, which silently duplicated the whole site when it pointed at an ancestor, while symlinked markdown files are read and an entry whose target cannot be resolved (dangling link, `ELOOP`) is skipped silently — deliberately unlike `assets::plan`, which errors on both; see RISK-5), `frontmatter.rs` (JSON frontmatter parse, BOM-tolerant), `page.rs` (`Page`, built in one step by `Page::new(fm, content, kind, path, site)`, which validates the date, then the tags, then the slug, so a frontmatter error wins over a file-name error; `parse_date`), `slug.rs` (`Slug`, crate-private: file-name validation and every slug rule — URL, output path, parent, top-level test, segments), `tag.rs` (`Tag`, crate-private: tag validation, de-duplication, tag page slug and URL), `summary.rs` (`PageSummary`, incl. `url`).
- `src/render/` — `markdown.rs` (pulldown-cmark → HTML with extensions), `template.rs` (Tera glob load; `page.html`, `section.html`, `home.html`, `tags.html` and `tag.html` template names are hardcoded here; `PageTemplate`/`SectionTemplate`/`HomeTemplate`/`TagTemplate` contexts plus `TagLink`/`TagIndexEntry`; constructs the template `Output`s (`render_page`, `render_section_page`, `render_home_page`, `render_tag_index`, `render_tag_page`), each with its `OutputKind` and a `Body::Template` whose context also gets `config`; this is why `render` imports `Output` from `build` (ARCH-5 moves construction into `build/generate/*`)).
- `src/build/` — `pipeline.rs` (`BuildOptions`, `BuildPlan` with private fields, `PlannedOutput`, `plan` and `commit`; `commit` is the only function in the crate that empties or writes the output folder, and it lives in the same module as `BuildPlan` so the fields never need to leave it; internally the plan stores full paths and `outputs()` presents them relative to `output_dir`), `clean.rs` (`clean` for `mango clean`, plus the crate-private `current_dir`, `ensure_safe_to_clean` and `clean_contents`), `output.rs` (the single output model: `Output { kind: OutputKind, body: Body }`, where `OutputKind` is `Page { slug, date }`, `Section`, `Home`, `TagIndex`, `Tag`, `Feed`, `Sitemap` or `Asset { folder, rel }` and `Body` is `Template { name, context }`, `Text` or `Copy(source)`; `Output::path(dist)` derives the location from the kind — slugs via `Slug::output_path` (`dist/<slug>/index.html`, the home slug → `dist/index.html`), `dist/feed.xml`, `dist/sitemap.xml`, `dist/<folder>/<rel>` — and `Display for OutputKind` gives the collision label; `check_collisions` over one `&[Output]`, exact and file-vs-folder; `render` to in-memory `RenderedOutput { path, contents: Contents::{Text, Copy} }`; `write` writes text and copies assets, naming the source on a copy failure (RISK-7)), `index/section.rs` (a `Section { pages, subsections }` for every ancestor folder of every page (found with `Slug::parent`), in a `BTreeMap<Slug, Section>`, so sections are generated in slug order; pages within a section sorted by `compare_summaries`: newest date first, undated last, ties by title then slug), `index/tag.rs` (`build_tag_index`: `BTreeMap<Tag, Vec<PageSummary>>`, each sorted by `compare_summaries`), `generate/{content,section,assets,home,tag,feed,sitemap,xml}.rs` (`home.rs` builds the home output from pages + section index and owns `recent_pages`, shared with the feed; `tag.rs` emits the tag index output first, then tag pages by name; `feed.rs`/`sitemap.rs` return `Option<Output>`, and `sitemap.rs` selects and dates entries with an exhaustive `match` on `OutputKind`; `xml.rs` is the escape helper; `assets.rs` has `plan` only (list files as `Asset` outputs with a `Copy` body, sorted by relative path, no I/O beyond reading the folder; entries are classified with `fs::metadata`, which follows symlinks, so a symlink to a folder is rejected with `MangoError::General` naming `asset '<rel>'` and a dangling link or link loop fails here — before cleaning — instead of in the commit-time copy after it; symlinks to files are planned normally and copied as their contents, and the assets root itself may be a symlink); the copy itself is done by `output::write`, and any copy failure fails the build).

## Conventions

- Errors: return `MangoError` via `?`; add variants to `src/error.rs` rather than ad-hoc strings where a category exists. Path-specific I/O errors go through `MangoError::io_at`.
- Git: GitHub flow. Work on a branch and land it on the integration branch (`master` today; `specs/constitution.md` has the resolution rule, which also covers `main`) through a **pull request** that the maintainer reviews and squash-merges on GitHub, one commit per backlog item or feature, with the item ID in the pull request's title (e.g. `… (RISK-2)`). The repository allows squash merges only, and the pull request's title and body become the commit. An agent pushes its branch and opens the pull request (`gh pr create`) only when the maintainer says “land it”, and never merges, approves or closes one; after the merge it pulls `master` and deletes the local branch (**Landing** in `specs/constitution.md`). Branches are `agents/claude/<id>-<short-desc>` for work done by an agent and `users/patrick/<id>-<short-desc>` for work done by hand; `<short-desc>` is two to four kebab-case words for the change, and the `<id>-` segment is dropped when there is no backlog item. Start from a clean `master` that is up to date with `origin`. To see a branch's change, diff against its branch point (`git diff <branch-point>..HEAD`) plus anything uncommitted — a bare `git diff` is empty once a pipeline run has checkpointed. The pull request's body is the squashed message and must stand alone, since the branch's own commits are discarded. Don't record commit hashes in `specs/_system/backlog.md`; squashing invalidates them, and `git log --grep='<ID>'` is the lookup that works.
- CLI: clap derive style.
- Tests: unit tests live in `#[cfg(test)] mod tests` next to the code (filesystem fixtures are created per test under `target/unit-fixtures/`); `tests/plan.rs` tests the pipeline **in-process** through the library's public API (`plan`/`commit`/`clean`), which is also the check that the seven re-exports are sufficient — it uses a minimal five-template theme so listing order can be asserted as exact strings, and never changes the cwd; the end-to-end tests (`tests/build.rs`) run the compiled binary — against `example/site` + `example/meta` into `target/integration-dist`, and against per-test temp sites under `CARGO_TARGET_TMPDIR` for error/draft cases. They assert on exit status, stderr and output files.
- `example/` is mango's example site (the fictional blog and projects of "Wren Calloway", with a full theme) and also the E2E fixture: `example/site`, `example/meta` and `example/mango.json` exercise **every success-path feature** with realistic content: a draft (`blog/incremental-builds.md`, whose `wip` tag must never appear), an undated page (`blog/reading-list.md`), two posts on the same date, duplicate tags (`blog/how-i-write.md`, which also uses every markdown extension), special characters (`blog/rust-and-wasm-canvas.md`), a top-level page (`about.md`), nested sections (`projects/hardware/keyboards`) where `projects` has only subsections, nested assets, `recent_count` truncation and a trailing-slash `base_url`. (`index.md` inside a section is covered by the temp-site test `build_allows_index_md_inside_section`.) Keep the content realistic: it is what new users see. `tests/build.rs` builds them once (`fixture_dist()`) and checks them in `build_generates_site_from_fixture` (exact output manifest), `fixture_internal_links_resolve` and the other `fixture_*` tests. When you add a feature, add fixture content for it and update the manifest and tests. Never put broken/error-case files there, since the build must succeed; build those in test code. `example/dist` is generated output and gitignored.

## Definition of done

A change is done only when all of these hold:

1. **The gate passes:** `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`. No new warnings, and no `#[allow]` added to hide one. Once the change is pushed, CI must be green on both Linux and Windows.
2. **Behavior is tested:** every behavior change or bug fix has a test that fails without it. Unit tests sit next to the code; anything visible from the CLI (exit code, stderr, output files) also gets an E2E test in `tests/build.rs`.
3. **The fixture covers it:** a new success-path feature has content in `example/site` / `example/meta` / `example/mango.json`, and the output manifest in `build_generates_site_from_fixture` plus a `fixture_*` test are updated. Error cases get temp-site E2E tests, never fixture files.
4. **Failures are safe and clear:** anything that can fail on bad input (content, file names, config, templates, assets, output conflicts) fails before the output folder is cleaned, proven with a `snapshot` test. The error is a `MangoError` printed to stderr with exit status 1, naming the file or path and the offending value.
5. **Output is valid and deterministic:** two builds of the same input are byte-identical (sorted listings, no timestamps in generated files), every internal link in the fixture output resolves (`fixture_internal_links_resolve`), and generated XML is escaped.
6. **No new dependencies** without the maintainer's explicit approval. Removing one is fine.
7. **Docs change with the code:** `README.md` for anything a site author sees (CLI flags, config fields, content rules, output URLs, templates), `CLAUDE.md` for architecture, pipeline order and conventions.
8. **Nothing is left half-done:** no TODO stubs, commented-out code, or `unwrap`/`expect` in production code. Known limitations are listed in `README.md`.
