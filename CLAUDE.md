# mango

A static site generator CLI written in Rust (edition 2024, toolchain pinned in `rust-toolchain.toml`). Licensed GPL-3.0-or-later (`LICENSE`). `README.md` is the user-facing guide; this file is for working on the code. Planned improvements and known gaps are tracked in `specs/_system/backlog.md`: check it before starting related work, and update an item's status when you pick it up or finish it.

Pipeline: load markdown files (`.md` / `.markdown`, any case) → parse frontmatter → load the site config → render markdown with pulldown-cmark → render through Tera templates → write `dist/<slug>/index.html` per page (plus a section index page for every folder level, the home page at `dist/index.html`, the tag index at `dist/tags/index.html` and one `dist/tags/<tag>/index.html` per tag) → write `dist/feed.xml` and `dist/sitemap.xml` (only when `base_url` is set) → copy assets into `dist/assets/`.

**Site config is JSON too** (`src/config.rs`, `SiteConfig`). `build --config <path>` (default `mango.json`, cwd-relative). The default file is optional (missing → defaults); an explicitly given `--config` that doesn't exist is an error naming the path. `#[serde(deny_unknown_fields)]`: malformed JSON, unknown fields (typos) or a bad `recent_count` fail with `MangoError::Config` naming the file. Fields, all optional: `title`, `author`, `description`, `base_url` (strings), `recent_count` (non-negative integer, default 10). `base_url`, when set, must start with `http://` or `https://` (case-sensitive prefix check; `""` and `example.com` are rejected) — otherwise `MangoError::Config`: `'<path>': invalid base_url '<value>': must start with http:// or https://`. Templates get `base_url` exactly as written; HTML output never uses it (generated HTML URLs stay root-relative). Only the feed and sitemap use it, via `config::base_url_root`, which trims trailing `/` so `https://example.com/` and `https://example.com` give identical links. The config file path is protected from cleaning (see below). See `example/mango.json`.

**File names are strict.** Every segment of a page's path relative to the site folder (folders and the file stem) may only contain ASCII letters, digits, `-`, `_` and `.` (`page::generate_slug`), so URLs, the feed and the sitemap never need percent-encoding. Anything else (spaces, non-ASCII, `+`) is a `General` build error naming the file and `'<segment>'`, drafts included.

**Tags are strict, like dates.** Each tag must match `^[a-z0-9]+(-[a-z0-9]+)*$` (lowercase ASCII letters/digits, single hyphens between; checked by hand in `page::validate_tags`, called from `Page::new`). Anything else — `""`, `Rust`, `static site`, `c++`, leading/trailing/double hyphens, non-ASCII — is a `Frontmatter` build error naming the file and `'<tag>'`, drafts included. Duplicate tags are dropped, first occurrence keeps its place. The tag is its own slug (no slugify): tag pages are at `/tags/<tag>/` (`page::tag_slug`), the tag index at `/tags/`. The tag index is **always** generated (even with no tags), so `/tags/` is reserved: a `tags/` content folder (`section index 'tags'`) or a top-level `tags.md` (`page 'tags'`) collides with `tag index` and fails the build.

**Feed and sitemap** (`build/generate/{feed,sitemap,xml}.rs`) are generated in Rust, not Tera (fixed format; escaping of `& < > " '` via `xml::escape`), and only when `base_url` is set — otherwise neither file is written and the build still succeeds. No `lastBuildDate`/`now()`; output is deterministic.
- `feed.xml` (collision source `RSS feed`): RSS 2.0; channel `title`/`description` from config (empty when unset), `link` `<base>/`; one `<item>` per entry of `home::recent_pages` (the same list as `home.recent`, in order) with `title`, `link` (`<base><url>`), `<guid isPermaLink="true">` (same), `description` (frontmatter), `pubDate` (`Sat, 24 Jan 2026 00:00:00 +0000`).
- `sitemap.xml` (collision source `sitemap`): sitemaps.org 0.9 `<urlset>`; one `<url><loc>` per HTML render item (home, pages, sections, tag index, tag pages — derived from the render items, not the content), sorted by `loc` as plain strings; `<lastmod>YYYY-MM-DD</lastmod>` only for dated content pages (`RenderItem.page_date`).

**Template contexts** (Tera autoescape is on for `.html`, so print URLs with `| safe`):
- every template: `config` — always has all five keys; unset strings are JSON `null` (renders empty, falsy, and triggers `default(...)`; `""` would not).
- `page.html`: `page` — `title`, `author`, `description`, `date`, `tags` (list of `{ name, url }` objects, `url` = `/tags/<name>/`, frontmatter order after dedup), `url` (`/<slug>/`), `content`.
- `section.html`: `section` — `slug`, `url`, `pages` (direct child page summaries: `title`, `date`, `slug`, `url`), `subsections` (direct child sections: `slug`, `url`, sorted by slug).
- `home.html`: `home` — `recent` (up to `config.recent_count` dated pages site-wide, section ordering, undated dropped) and `sections` (top-level sections: `slug`, `url`, `page_count` = direct child pages).
- `tags.html`: `tags` — the list itself (not wrapped): `{ name, url, page_count }` sorted by name; empty when no page has tags.
- `tag.html`: `tag` — `name`, `url`, `pages` (page summaries with that tag, section ordering, undated included and last).
- Page summaries (`section.pages`, `home.recent`, `tag.pages`) have no `tags` key.
- `page.html`, `section.html`, `home.html`, `tags.html` and `tag.html` are all required (names hardcoded in `render/template.rs`); a missing one fails at render time, before cleaning (`tags.html` is needed by every build; `tag.html` by any build with at least one tag).

**Markdown extensions** enabled in `render/markdown.rs`: tables, footnotes, strikethrough, task lists, explicit heading attributes (`# Title {#my-id}`). No auto-generated heading IDs.

**Frontmatter is JSON, not YAML** — a `---`-delimited block containing a JSON object (see `example/site/blog/how-i-write.md`); a leading UTF-8 byte order mark is ignored. Line endings may be LF, CRLF or a mix: `str::lines` drops the `\r`, so the delimiters match and the JSON block is re-joined with `\n`, and the body is normalized to LF (its final newline dropped), so a CRLF content file and its LF twin build byte-identical output. The one exception is the "no frontmatter" early return, which hands the content back verbatim, CRLF included; it is unreachable from the CLI, since `loader::load` turns it into the missing-frontmatter error. Only content is normalized: templates are rendered and assets copied with whatever line endings they have. Pinned by the CRLF tests in `frontmatter.rs` and `tests/build.rs`; TEST-1 in `specs/_system/backlog.md` records what each of them can and cannot catch. Required fields: `title`, `author`, `description`, `draft`; optional: `date`, `tags` (see the tag rules above). `date` must be a strict `YYYY-MM-DD` string (parsed into `Option<chrono::NaiveDate>` by `page::parse_date`); a present but invalid or impossible date — including `""`, and on draft pages — is a build error naming the file and the value. Templates still see `page.date` / `section.pages[].date` as `"YYYY-MM-DD"`, or `""` when unset. A markdown file without frontmatter (`<file>: missing frontmatter: …`) or with malformed frontmatter, at any depth, is a build error naming the file. Pages with `"draft": true` are still parsed but excluded from output and section indexes (filtered in `loader::load`).

## Commands

```sh
cargo build
cargo test          # unit tests + tests/build.rs integration tests (fixture build + temp-site error cases)
cargo clippy --all-targets -- -D warnings
cargo fmt

# Run against the fixture site (paths are cwd-relative!):
cd example && cargo run -- build
# or from the repo root:
cargo run -- build --site example/site --templates example/meta/templates --assets example/meta/assets -o example/dist
```

**Path gotcha:** all CLI paths resolve relative to the current working directory, with defaults `site/`, `meta/templates/`, `meta/assets/`, `dist/`. The repo root has none of these — the sample site lives under `example/` (`example/site`, `example/meta`; generated `example/dist` is gitignored).

## CLI surface (`src/cli.rs`)

- `build` — the only real subcommand; `build()` in cli.rs is the orchestration point wiring the whole pipeline. Order: load pages → load config → load templates → resolve assets destination (an assets path with no final name, e.g. `.`/`..`, is an error) → plan assets (`assets::plan` lists every asset file; a missing assets folder fails here, as does a symlinked folder or an unresolvable symlink inside the assets folder) → build render items (pages, section indexes, home page, then tag index + tag pages) → build generated files in memory (`feed.xml`, `sitemap.xml` from the render items; skipped without `base_url`) → collision check (render items in that order, then generated files, then asset files) → render **every** page, section, home, tag item to strings in memory (generated files mapped via `output::render_generated`) → safety check → empty the output folder → write rendered and generated files → copy the planned assets. Nothing is deleted or written until loading, planning and rendering have succeeded, so a bad page, bad file name, bad tag, bad config (incl. `base_url`), missing templates or assets folder, an output conflict or a Tera render error leaves the previous output untouched (an I/O failure after the clean can still leave partial output).
  - **Collisions:** two outputs mapping to the same file (e.g. top-level `posts.md` and the `posts/` section index — including an ancestor index: `a.md` next to `a/b/c.md`; `tags.md` / a `tags/` folder vs the tag index; `site/assets.md` vs an asset `index.html`) fail with `MangoError::General` naming the path and both sources (`page '<slug>'`, `section index '<slug>'`, `home page`, `tag index`, `tag page '<tag>'`, `RSS feed`, `sitemap`, `asset '<relative path>'`). So does a file-vs-folder conflict, where one output is a file at a path another output needs as a directory (`site/feed.xml.md` → `dist/feed.xml/index.html` vs `dist/feed.xml`; `site/assets/minimal/main.css.md` vs the asset `minimal/main.css`). `posts/index.md` → `posts/index/index.html` is not a collision.
  - **Cleaning:** the output folder's contents are removed (folder kept, symlinks removed not followed; a symlink `remove_file` can't delete falls back to `remove_dir`, for Windows directory links). `ensure_safe_to_clean` refuses an output path that is the cwd, a parent of the cwd, or equal to / a parent of the site, templates or assets folder or the config file (canonicalized comparison).
- `clean` — removes the dist dir; a missing dir is success. Same safety check, protecting the cwd, its parents, and the default `site`, `meta/templates`, `meta/assets` (not the config file; `clean` has no `--config`).
- `run` (dev server) — not implemented; takes no options, returns an error and exits 1. There is no `publish` subcommand: it was dropped rather than implemented (backlog FEAT-2), so `mango publish` is a clap “unrecognized subcommand” error, pinned by `publish_is_not_a_command`. Add `run`'s flags and a server dependency (with approval) when it is implemented, not before: unused code is removed, never kept behind `#[allow(dead_code)]`.

## Module map

- `src/main.rs` — entry; calls `cli::run()`. On error prints to **stderr** and exits 1; exits 0 on success.
- `src/config.rs` — `SiteConfig`, `load(path, explicit)` (incl. `base_url` validation) and `base_url_root`.
- `src/error.rs` — `MangoError` (thiserror): `Io`, `IoPath { path, source }`, `Frontmatter`, `General`, `Config`, `Template`. Display includes the underlying cause (for `Template`, the full Tera `source()` chain). Use `MangoError::io_at(path, e)` for I/O failures on a specific file/dir.
- `src/content/` — `loader.rs` (recursive site traversal; `is_markdown`; propagates errors at every depth; drops drafts; classifies each entry with `fs::metadata` plus a non-following `is_symlink` check before descending, so a symlinked folder is a `General` error (`content folder '<rel>' is a symlink to a directory`) instead of being followed and re-walked, which silently duplicated the whole site when it pointed at an ancestor, while symlinked markdown files are read and an entry whose target cannot be resolved (dangling link, `ELOOP`) is skipped silently — deliberately unlike `assets::plan`, which errors on both; see RISK-5), `frontmatter.rs` (JSON frontmatter parse, BOM-tolerant), `page.rs` (`Page`, `generate_slug` with file-name validation, `slug_url`, `tag_slug`, `parse_date`, `validate_tags`), `summary.rs` (`PageSummary`, incl. `url`).
- `src/render/` — `markdown.rs` (pulldown-cmark → HTML with extensions), `template.rs` (Tera glob load; `page.html`, `section.html`, `home.html`, `tags.html` and `tag.html` template names are hardcoded here; `PageTemplate`/`SectionTemplate`/`HomeTemplate`/`TagTemplate` contexts plus `TagLink`/`TagIndexEntry`; each render item also gets `config`; `RenderItem.page_date` is set only for content pages).
- `src/build/` — `output.rs` (`check_collisions` over render items + `GeneratedFile`s + `AssetFile`s, exact and file-vs-folder; `render` to in-memory `RenderedFile`s, `render_generated`, `write`; slug → `dist/<slug>/index.html`, slug `""` → `dist/index.html`, generated files → `dist/<path>`), `index/section.rs` (a `Section { pages, subsections }` for every ancestor folder of every page, in a `BTreeMap`, so sections are generated in slug order; pages within a section sorted by `compare_summaries`: newest date first, undated last, ties by title then slug), `index/tag.rs` (`build_tag_index`: `BTreeMap<tag, Vec<PageSummary>>`, each sorted by `compare_summaries`), `generate/{content,section,assets,home,tag,feed,sitemap,xml}.rs` (`home.rs` builds the home item from pages + section index and owns `recent_pages`, shared with the feed; `tag.rs` emits the tag index item first, then tag pages by name; `feed.rs`/`sitemap.rs` return `Option<GeneratedFile>`; `xml.rs` is the escape helper; `assets.rs` has `plan` (list files, no I/O beyond reading the folder; entries are classified with `fs::metadata`, which follows symlinks, so a symlink to a folder is rejected with `MangoError::General` naming `asset '<rel>'` and a dangling link or link loop fails here — before cleaning — instead of in `copy` after it; symlinks to files are planned normally and copied as their contents, and the assets root itself may be a symlink) and `copy`; any copy failure fails the build).

## Conventions

- Errors: return `MangoError` via `?`; add variants to `src/error.rs` rather than ad-hoc strings where a category exists. Path-specific I/O errors go through `MangoError::io_at`.
- Git: work on a branch and land it on the integration branch (`master` today; `specs/constitution.md` has the resolution rule, which also covers `main`) by **squash merge**, one commit per backlog item or feature, with the item ID in the subject (e.g. `… (RISK-2)`). Branches are `agents/claude/<id>-<short-desc>` for work done by an agent and `users/patrick/<id>-<short-desc>` for work done by hand; `<short-desc>` is two to four kebab-case words for the change, and the `<id>-` segment is dropped when there is no backlog item. Start from a clean `master`. To see a branch's change, diff against its branch point (`git diff <branch-point>..HEAD`) plus anything uncommitted — a bare `git diff` is empty once a pipeline run has checkpointed. The squashed message must stand alone, since the branch's own commits are discarded. Don't record commit hashes in `specs/_system/backlog.md`; squashing invalidates them, and `git log --grep='<ID>'` is the lookup that works.
- CLI: clap derive style.
- Tests: unit tests live in `#[cfg(test)] mod tests` next to the code (filesystem fixtures are created per test under `target/unit-fixtures/`); the end-to-end tests (`tests/build.rs`) run the compiled binary — against `example/site` + `example/meta` into `target/integration-dist`, and against per-test temp sites under `CARGO_TARGET_TMPDIR` for error/draft cases. They assert on exit status, stderr and output files.
- `example/` is mango's example site (the fictional blog and projects of "Wren Calloway", with a full theme) and also the E2E fixture: `example/site`, `example/meta` and `example/mango.json` exercise **every success-path feature** with realistic content: a draft (`blog/incremental-builds.md`, whose `wip` tag must never appear), an undated page (`blog/reading-list.md`), two posts on the same date, duplicate tags (`blog/how-i-write.md`, which also uses every markdown extension), special characters (`blog/rust-and-wasm-canvas.md`), a top-level page (`about.md`), nested sections (`projects/hardware/keyboards`) where `projects` has only subsections, nested assets, `recent_count` truncation and a trailing-slash `base_url`. (`index.md` inside a section is covered by the temp-site test `build_allows_index_md_inside_section`.) Keep the content realistic: it is what new users see. `tests/build.rs` builds them once (`fixture_dist()`) and checks them in `build_generates_site_from_fixture` (exact output manifest), `fixture_internal_links_resolve` and the other `fixture_*` tests. When you add a feature, add fixture content for it and update the manifest and tests. Never put broken/error-case files there, since the build must succeed; build those in test code. `example/dist` is generated output and gitignored.

## Definition of done

A change is done only when all of these hold:

1. **The gate passes:** `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test`. No new warnings, and no `#[allow]` added to hide one.
2. **Behavior is tested:** every behavior change or bug fix has a test that fails without it. Unit tests sit next to the code; anything visible from the CLI (exit code, stderr, output files) also gets an E2E test in `tests/build.rs`.
3. **The fixture covers it:** a new success-path feature has content in `example/site` / `example/meta` / `example/mango.json`, and the output manifest in `build_generates_site_from_fixture` plus a `fixture_*` test are updated. Error cases get temp-site E2E tests, never fixture files.
4. **Failures are safe and clear:** anything that can fail on bad input (content, file names, config, templates, assets, output conflicts) fails before the output folder is cleaned, proven with a `snapshot` test. The error is a `MangoError` printed to stderr with exit status 1, naming the file or path and the offending value.
5. **Output is valid and deterministic:** two builds of the same input are byte-identical (sorted listings, no timestamps in generated files), every internal link in the fixture output resolves (`fixture_internal_links_resolve`), and generated XML is escaped.
6. **No new dependencies** without the maintainer's explicit approval. Removing one is fine.
7. **Docs change with the code:** `README.md` for anything a site author sees (CLI flags, config fields, content rules, output URLs, templates), `CLAUDE.md` for architecture, pipeline order and conventions.
8. **Nothing is left half-done:** no TODO stubs, commented-out code, or `unwrap`/`expect` in production code. Known limitations are listed in `README.md`.
